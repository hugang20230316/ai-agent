# 异步事件溯源排查参考

这份参考用于“现象发生在异步链路，但最终只看到下游错误”的缺陷。它描述如何重建可验证的事件时间线，不假设系统一定采用事件溯源架构，也不要求存在不可变事件表。

## 何时启用

只要问题涉及任务/作业、消息队列、回调、轮询、最终一致、延迟落库、重试、重复投递或乱序处理，就启用本参考；同步请求、纯界面、认证/网络和单库静态数据问题不主动启用，除非代码或运行证据出现异步边界。

## 固定排查问题

逐项回答，不能用一段笼统叙述替代；每项标记 `已证实`、`未命中范围`、`未验证`、`需补证据` 或 `不适用`。

1. 入口是什么？请求、定时任务、事件或人工操作的业务语义、输入和返回结果是什么？
2. 哪个组件产生了事件？生产时间、业务 ID、任务 ID、消息 ID、Trace ID、回调 ID 和重试/尝试序号分别是什么？
3. 消息是否投递、持久化和重新投递？生产者、队列/主题、分区或分片、投递结果和消费时间是什么？
4. 哪个消费者处理？消费输入、输出变化、异常、幂等判断和重试结果是什么？
5. 是否存在回调或后续事件？它的生产者、接收者和关联 ID 是否能逐跳对应？
6. 哪一次持久化写入改变了业务不变量？是新增、更新、删除、软删除、覆盖还是回滚？
7. 用户可见读取查到的是什么？它代表历史事件、处理后状态还是当前快照？
8. 事件发生时间、处理时间、观测时间和查询时间是否混用？是否存在延迟、并发、重试或乱序？
9. 日志查询的服务/日志源、环境、日期分片或集合、时间窗是否与事件时间一致？0 命中到底是无事件还是查错范围？
10. 日志窗口对应的部署版本、镜像标签或提交是什么？当前代码是否能代表该窗口？
11. 当前状态与历史证据冲突时，分别保留什么事实？哪些只是代码推断？
12. 已知影响、未覆盖路径、缺失的审计/CDC/MQ 元数据和下一条最小证据是什么？

## 事件时间线与证据矩阵

先用业务 ID 找到事件，再把关联 ID 逐跳补齐；每一行只填实际观察到的值，不要凭字段名猜含义。

```text
阶段              服务/日志源       关联标识              事件时间        处理时间        观测时间        输入 -> 输出       状态
入口/创建          <日志源>          <业务/任务标识>        <时间>          <时间>          <时间>          <值变化>          已证实/...
事件生产          <日志源>          <消息/跟踪标识>        <时间>          <时间>          <时间>          <值变化>          已证实/...
投递/消费          <日志源>          <消息/尝试标识>        <时间>          <时间>          <时间>          <值变化>          已证实/...
回调/后续事件      <日志源>          <回调/跟踪标识>        <时间>          <时间>          <时间>          <值变化>          已证实/...
持久化写入         <日志源>          <任务/业务标识>        <时间>          <时间>          <时间>          <值变化>          已证实/...
用户可见读取       <日志源>          <业务/任务标识>        <时间>          <时间>          <时间>          <值变化>          已证实/...
```

关联键必须带环境和租户作用域（如果系统有租户），并注明来源。Trace 缺失时可降级到消息/任务/回调 ID；所有关联键都缺失时标记 `需补证据`，不得按相似时间拼链。

## 查询顺序与只读模板

按“最小、独立、可复核”的顺序查询：入口日志 -> 事件生产 -> 投递/消费 -> 回调/写入 -> 当前读取。每个阶段选择一个能直接证明该阶段的后端源；总体验证至少覆盖日志和业务数据/队列中的两类独立证据。先确认环境和部署版本，再执行查询。

Grafana 或同类日志工具使用本机配置的入口，命令只保留占位符（命令选项名称保持工具原文）：

```console
python3 <grafana-skill>/scripts/grafana.py query-logs \
  --app <服务> --namespace <环境> \
  --query '<业务或消息标识>' \
  --from-value '<事件时间减窗口>' \
  --to-value '<事件时间加窗口>' --limit 100
```

生产关系库只能在用户可查询且规则允许时提供一条无变量、只读、限定业务对象和时间窗的语句；不要把多个检查拼成脚本，也不要提供写操作：

```sql
SELECT <最小字段>
FROM <业务表>
WHERE <业务标识> = '<值>'
  AND <事件或更新时间> >= '<开始时间>'
  AND <事件或更新时间> < '<结束时间>'
ORDER BY <事件或更新时间>;
```

模板不得写入真实 UUID/GUID、队列名、内网域名/IP、账号、token、cookie、机器绝对路径或完整原始 payload；真实响应保存到临时目录，最终只输出必要字段。
文档中的示例域名统一使用 `example.test` 或 `example.com`，仅作占位符。

## 时序判定规则

- 事件先生产、后删除、再消费：按三个实际时间点说明“已入队但消费时前置状态已不存在”，不能只看当前行。
- 删除先完成、后收到迟到事件：检查幂等、墓碑/软删除和是否允许复活，不能把迟到消息自动解释成新建。
- 失败后重试成功：历史失败仍是事实，当前成功只说明后续状态；两者必须分别标注来源和时间。
- 当前数据库有一条或多条记录：只能证明查询时快照，不能反推此前没有短暂空窗或删除。
- 单一日志源、服务或日期分片 0 命中：先检查映射和分片；映射不明或权限不足时记录精确阻塞项。

## 结论格式

结论至少分开写：

- `事实`：日志、数据库、队列或接口直接记录的值及其时间。
- `代码推断`：根据当前或已绑定版本代码重建的调用关系，不能替代运行证据。
- `证据缺口`：未查到、查错范围、无权限、版本未绑定或缺少审计/消息元数据。
- `影响与动作`：用户可见影响，以及应执行的代码修复、数据修复、读侧兼容或补证据动作；没有实际执行的动作不得写成已完成。

输出时逐项保留固定问题的状态，尤其是 0 命中、当前快照、版本差异和未验证路径。
